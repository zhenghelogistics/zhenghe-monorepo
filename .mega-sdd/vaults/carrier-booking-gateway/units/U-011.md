# Unit U-011 — Implement statusReconciler — the single writer of booking status and events

## Goal

Implement `reconcile(bookingId, observedStatus, source, raw?)` — the only function in the system that updates `bookings.status` or appends `booking_events` — enforcing the allowed-transition table and recording an audit row per real change.

## Context (read first)

Per spec §9 and decision D-009, submit results, poll results, cancel results, and any future webhook all funnel through this one choke point. On a legal transition it updates `bookings.status`, `carrier_status_raw`, `last_carrier_sync_at` and appends a `STATUS_CHANGE` `booking_events` row with `from`/`to`/`source`/`actor`/correlation id. On an illegal transition it logs and drops — never applies. On no change it touches only `last_carrier_sync_at`. `bookingEvents.ts` owns the append-with-monotonic-`seq` helper.

## Anchors

- packages/carrier-core/src/status.ts — CanonicalBookingStatus, ALLOWED_TRANSITIONS, isAllowedTransition
- apps/booking/src/db/rowTypes.ts — BookingRow, BookingEventRow

## Hard rules

- NEVER issue an UPDATE on bookings.status or an INSERT into booking_events outside statusReconciler.ts / bookingEvents.ts (constitution C-002)
- NEVER apply an illegal status transition; log and drop it (constitution C-004)
- DO NOT UPDATE or DELETE a booking_events row; the table is append-only (constitution F-001)
- ALWAYS write from_status, to_status, source, actor, and a correlation id on every booking_events row

## Implementation steps

1. Write `bookingEvents.ts` with `appendEvent(client, { bookingId, eventType, fromStatus, toStatus, source, actor, detail })` that computes the next `seq` for that booking inside the same transaction and inserts the row.
2. Write `statusReconciler.ts` exporting `reconcile(deps, bookingId, observed, source, raw?)`: load the current status inside a transaction; if `observed === current`, update only `last_carrier_sync_at`; if `isAllowedTransition(current, observed)`, update `bookings` and `appendEvent` a `STATUS_CHANGE`; otherwise log a warning with both statuses and return without writing.
3. Provide a sibling `recordError(deps, bookingId, source, error)` that appends an `ERROR` event and, when the error is terminal for submit/cancel, transitions to `SUBMISSION_FAILED` / `CANCELLATION_FAILED` through the same guarded path.
4. Write `statusReconciler.test.ts` against a test Postgres: a legal `SUBMITTED -> PENDING_CONFIRMATION` writes one event; an illegal `CONFIRMED -> PENDING_SUBMISSION` writes nothing; a same-status observe bumps only `last_carrier_sync_at`; `seq` is contiguous per booking.

## Out of scope

- The `booking_events` read API (U-016).
