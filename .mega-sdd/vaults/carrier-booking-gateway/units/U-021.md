# Unit U-021 — Implement the Maersk (MAEU) carrier adapter

## Goal

Implement the Maersk adapter with OAuth2 client-credentials + the static `Consumer-Key` header, DCSA-aligned request/status/tracking mapping, and a contract test that passes `runContractSuite` against the Maersk mock.

## Context (read first)

Per spec §10, Maersk (SCAC `MAEU`) authenticates with an OAuth2 client-credentials token AND a `Consumer-Key` header on every request, and its sandbox runs on a separate host (so `base_url` differs). Booking is DCSA-aligned; tracking comes from Maersk's Track & Trace events API. Quirks stay inside this folder; the adapter never touches the DB.

## Anchors

- packages/carrier-core/src/auth/oauth2ClientCredentials.ts — extraHeaders carries Consumer-Key
- packages/carrier-core/src/adapter.ts — CarrierAdapter surface
- apps/mock-carriers/src/carriers/maersk.ts — the mock contract to code against

## Hard rules

- NEVER import from apps/booking/src/db or issue SQL in apps/booking/src/adapters/maersk (constitution C-001)
- ALWAYS send the Consumer-Key header alongside the bearer token on every Maersk request
- NEVER let a Maersk status string cross the adapter boundary; only toCanonicalStatus output does (spec §5)
- file:apps/booking/src/adapters/maersk/*.ts MUST follow camelCase naming

## Implementation steps

1. Write `mapRequest.ts` (canonical → Maersk DCSA-shaped booking) and `mapStatus.ts` (`toCanonicalStatus`) covering every status the Maersk mock emits.
2. Write `mapTracking.ts` turning Maersk Track & Trace events into `NormalizedEvent[]` with a stable `dedupeKey`.
3. Write `index.ts` implementing `CarrierAdapter` (`code: 'MAEU'`, `transport: 'REST'`), configuring the OAuth2 strategy with `extraHeaders: { 'Consumer-Key': ... }`, calling `ctx.http.request` against the Maersk paths, classifying errors.
4. Write `maersk.contract.test.ts` booting the Maersk mock and running `runContractSuite`.
5. Add `README.md` noting the dual-auth requirement, the separate sandbox host, and sandbox open questions.
