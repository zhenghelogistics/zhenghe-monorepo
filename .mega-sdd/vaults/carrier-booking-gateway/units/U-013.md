# Unit U-013 — Implement worker tasks and cron enqueuers (submit / poll status / poll tracking / cancel)

## Goal

Implement the four graphile-worker tasks and the two cron enqueuers from flows F-S-001..F-S-004, plus the `AdapterContext` builder that binds credential + HTTP client + logger + a `carrier_messages` writer.

## Context (read first)

Per spec §9. This is where carrier calls actually happen — always inside a job, never in a request (constitution C-005 / D-001). `submit_booking` guards on `status === PENDING_SUBMISSION`, calls `adapter.createBooking`, and reconciles the ack or the failure. `poll_booking_status` maps the carrier status through `adapter.toCanonicalStatus` and calls `reconcile`; reaching `CONFIRMED` enqueues `poll_tracking`. `poll_tracking` upserts `shipment_events` by `dedupe_key` and never changes booking status. `submit_cancellation` calls `adapter.cancelBooking`. Two crons enqueue polls for the active set and the confirmed set on configurable intervals.

## Anchors

- apps/booking/src/domain/bookingService.ts — the enqueue helpers this worker's tasks are the consumers of
- apps/booking/src/worker/adapterContext.ts — builds AdapterContext from CredentialStore + carrier-core HttpClient
- packages/carrier-core/src/http/client.ts — createHttpClient (onExchange writes carrier_messages here)

## Hard rules

- NEVER call a carrier HTTP endpoint directly from a worker task; call the adapter (constitution D-001)
- ALWAYS route status changes through reconcile / recordError (constitution C-002)
- DO NOT act in submit_booking / submit_cancellation when the booking is no longer in the expected status (constitution E-003)
- NEVER change bookings.status from poll_tracking (constitution D-005)
- ALWAYS redact carrier_messages request bodies before insert (constitution B-003)

## Implementation steps

1. Write `adapterContext.ts` exporting `buildContext(carrierCode, correlationId)` that resolves the credential via `CredentialStore`, builds an `HttpClient` bound to that carrier's `base_url` and auth strategy, wires `onExchange` to insert a redacted `carrier_messages` row, and attaches a correlation-aware pino child logger and `clock`.
2. Write `tasks.ts` with `submitBooking`, `pollBookingStatus`, `pollTracking`, `submitCancellation` per the F-S flows, each loading the booking, resolving its adapter from the registry, building context, calling the adapter, and routing the result through `reconcile` / `recordError`; on `retryable` errors, throw so graphile-worker retries with backoff to `maxAttempts`, then record `SUBMISSION_FAILED` / `CANCELLATION_FAILED`.
3. Write `cron.ts` scheduling `poll_booking_status` for every booking in the active set every `POLL_INTERVAL_BOOKING_MIN`, and `poll_tracking` for every `CONFIRMED` booking every `POLL_INTERVAL_TRACKING_MIN`.
4. Write `index.ts` starting the graphile-worker runner with the task list and cron in the same process as the API (per D-002 the service is one deployable).
5. Write `tasks.test.ts` against a test Postgres with a `FakeAdapter` (from U-014's fixture path or an in-file stub): a successful `submitBooking` moves `PENDING_SUBMISSION -> SUBMITTED` and enqueues a status poll; a `retryable` failure exhausts retries to `SUBMISSION_FAILED` with an ERROR event; `pollTracking` upserts events idempotently by `dedupe_key`.
