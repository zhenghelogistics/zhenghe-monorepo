# Unit U-002 — Scaffold apps/booking (Fastify service + env config + health route)

## Goal

Stand up the `apps/booking` backend package: a Fastify server bootstrap, a zod-validated environment loader, and a `/health` route that will grow to report DB and worker state.

## Context (read first)

Runs after U-001 gives the workspace. Per `vault.md ## Architecture` and spec §4/§7/§16, `apps/booking` is one deployable service (API routes + worker in one process, added later) written against Fastify with normal routes. This unit ships only the shell: a `server.ts` that builds a Fastify instance and registers a `health` route, an `env.ts` that parses `process.env` through a zod schema and fails fast on missing keys, and an `index.ts` entrypoint. The user-visible outcome is a service that boots and answers `GET /health`.

## Anchors

- .env.example — the key list env.ts must validate (created in U-001)

## Hard rules

- NEVER read process.env outside apps/booking/src/config/env.ts
- ALWAYS validate route input with a zod schema at the boundary (constitution A-003)
- DO NOT use serverless handlers; use Fastify routes (constitution A-004)

## Implementation steps

1. Create `apps/booking/package.json` (name `@zhenghe/booking`) depending on Fastify, zod, pino, and the workspace `@zhenghe/config`; add `dev`, `build`, `test` scripts.
2. Write `src/config/env.ts` exporting a parsed, typed `env` object built from a zod schema covering every `.env.example` key; throw a readable error listing missing keys on failure.
3. Write `src/server.ts` exporting `buildServer()` that creates a Fastify instance with pino logging (level from `env.LOG_LEVEL`) and a request-id / correlation-id hook, then registers the health route.
4. Write `src/api/health.ts` as a Fastify plugin exposing `GET /health` returning `{ db: 'unconfigured', worker: { lastHeartbeatAt: null }, carriers: [] }` for now — later units fill the real checks.
5. Write `src/index.ts` that calls `buildServer()` and listens on a configurable port.
