# Unit U-016 — Implement the /bookings API routes

## Goal

Expose the booking endpoints from `vault.md ## Architecture` API contracts: `POST /bookings` (with `Idempotency-Key`), `GET /bookings` (filter + paginate), `GET /bookings/:id`, `POST /bookings/:id/cancel`, `POST /bookings/:id/refresh`, `GET /bookings/:id/events`, `GET /bookings/:id/tracking`.

## Context (read first)

Per spec §7 and flows F-U-001 / F-U-002. Each route is a thin Fastify handler: validate params/body with a zod schema, call the matching `bookingService` / `trackingService` function, map the result to the documented status code (`202` for create/cancel/refresh, `200` for reads), and shape errors consistently. Mutating routes use `requireRole('controller')` (or `admin`); reads use `requireRole('viewer')`. All timestamps out are ISO-8601 UTC.

## Anchors

- apps/booking/src/domain/bookingService.ts — createBooking, requestCancel, requestRefresh, getBookingDetail
- apps/booking/src/domain/trackingService.ts — queryEvents
- packages/carrier-core/src/schemas.ts — canonical request schema reused for POST /bookings validation

## Hard rules

- ALWAYS validate route input with a zod schema at the boundary (constitution A-003)
- NEVER trust a client-sent role; gate mutating routes with requireRole (constitution B-004)
- NEVER write bookings.status directly from a route; go via bookingService / reconcile (constitution C-002)
- ALWAYS return response timestamps as ISO-8601 UTC (constitution F-004)

## Implementation steps

1. Write `schemas/bookings.ts` with zod schemas: the create body (re-exporting `canonicalBookingRequestSchema`), the list query (`status`, `carrier`, `pol`, `pod`, `dateFrom`, `dateTo`, `customerRef`, `page`, `pageSize`), and the cancel body (`reason?`).
2. Write `bookings.ts` as a Fastify plugin registering all seven routes; `POST /bookings` reads the optional `Idempotency-Key` header and passes it to `createBooking`, returning `202 { bookingId, status }`; `GET /bookings` returns `{ items, page, pageSize, total }`; `GET /bookings/:id` returns the detail bundle; cancel/refresh return `202`.
3. Map service rejections: validation → `400` with field errors; cancel-not-allowed → `409`; unknown id → `404`.
4. Write `bookings.test.ts` using Fastify `inject` with a stubbed service layer: create returns 202 and echoes the id; a repeated idempotency key returns the same id; a `viewer` token on `POST /bookings` → 403; an invalid body → 400; `GET /bookings` paginates.
