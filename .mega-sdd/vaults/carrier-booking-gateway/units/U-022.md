# Unit U-022 — Implement the HMM (HDMU) carrier adapter

## Goal

Implement the HMM adapter with API-key auth and mapping for HMM's partly-proprietary booking payload, plus a contract test against the HMM mock.

## Context (read first)

Per spec §10, HMM (SCAC `HDMU`) uses an API key, its portal and some docs are in Korean, and its DCSA adoption is partial — the booking payload may be proprietary rather than pure DCSA. The mapping is therefore best-effort against the provisional HMM mock shape and will need revision once the sandbox is available. Quirks stay inside this folder; the adapter never touches the DB.

## Anchors

- packages/carrier-core/src/auth/apiKeyHeader.ts — makeApiKeyHeader
- packages/carrier-core/src/adapter.ts — CarrierAdapter surface
- apps/mock-carriers — the HMM namespace (added here or in U-019) is the contract to code against

## Hard rules

- NEVER import from apps/booking/src/db or issue SQL in apps/booking/src/adapters/hmm (constitution C-001)
- NEVER let an HMM status string cross the adapter boundary; only toCanonicalStatus output does (spec §5)
- ALWAYS isolate the proprietary-shape mapping in mapRequest.ts / mapStatus.ts so it can be replaced after sandbox access
- file:apps/booking/src/adapters/hmm/*.ts MUST follow camelCase naming

## Implementation steps

1. Add or finalize the HMM namespace in `apps/mock-carriers` reflecting the provisional proprietary shape (create/status/tracking/cancel).
2. Write `mapRequest.ts` (canonical → HMM payload) and `mapStatus.ts` (`toCanonicalStatus`) covering every status the HMM mock emits.
3. Write `mapTracking.ts` → `NormalizedEvent[]` with a stable `dedupeKey`.
4. Write `index.ts` implementing `CarrierAdapter` (`code: 'HDMU'`, `transport: 'REST'`) with the API-key strategy and error classification.
5. Write `hmm.contract.test.ts` running `runContractSuite` against the HMM mock.
6. Add `README.md` recording the Korean-language portal, the API-key header, and the sandbox-onboarding open questions.
